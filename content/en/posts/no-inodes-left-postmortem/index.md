# No Inodes Left: Minecraft Server Postmortem

## Summary

The Minecraft server became unreachable and was reported offline by a user.  
From the outside, the system appeared healthy: network access, SSH, and basic connectivity were all functional.

The root cause was not disk space exhaustion, but inode exhaustion caused by uncontrolled log file creation.

## Impact

- Minecraft server became unavailable
- Existing world data was corrupted
- New world had to be created
- No monitoring or alerting detected the issue
- Incident was only discovered through user report

## Detection

The issue was first reported by a friend who noticed the server was offline.

Initial checks showed no obvious failures:

- Ping: OK  
- SSH access: OK  
- Network connectivity: OK  
- Container health check: unhealthy  

Despite this, no external symptoms immediately explained the failure.

## Investigation

The debugging process followed standard system checks:

1. **Container logs**
   - No obvious errors or crash messages

2. **System resource usage**
   - CPU usage: normal
   - Memory usage: normal

3. **Disk space**
   - `df` showed available disk space

At this point, the system appeared fully operational from a traditional resource perspective.

However, the service still failed to operate correctly.

## Root Cause Analysis

The missing factor was inode exhaustion.

Running:

```
df -i
```

revealed:

- inode usage: 100%

Further inspection of the server directory showed:

- Millions of small log files generated by the server
- No log rotation configured
- Continuous file creation until inode exhaustion

Once inodes were exhausted:

- The system could no longer create new files
- Minecraft server could not write world data
- World corruption occurred due to failed write operations

## Resolution

Immediate actions:

- Stopped the Minecraft container
- Removed excessive log files
- Freed inode capacity
- Restarted the service with a fresh world

## Preventive Measures

To prevent recurrence:

- Enabled log rotation for all server logs
- Added cleanup strategy for high-frequency log generation
- Planned addition of monitoring for filesystem inode usage
- Identified need for backups (not yet implemented at the time)

## Lessons Learned

- Disk usage is not the only filesystem limitation — inode exhaustion is equally critical
- “System looks fine” is not a reliable indicator of service health
- Logging without rotation can silently degrade systems over time
- Observability (metrics + alerts) is necessary to detect non-obvious failures
- Backups are essential once data loss becomes a realistic failure mode
